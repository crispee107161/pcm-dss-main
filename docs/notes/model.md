Pearson correlation — the descriptive layer; quantifies relationships between metrics (e.g., spend ↔ reach, reach ↔ messaging contacts) for the dashboards.
Multiple Linear Regression (MLR) — the explanatory layer; models the conversion chain spend → reach → messaging contacts → purchases, which is why I built those correlations into the ads data at realistic strengths (0.84–0.99).
Holt-Winters exponential smoothing — the forecasting layer; this is what your system actually runs after your groupmate's Claude Code session evaluated it as the right fit (trend + seasonality, modest data needs — and the dataset has both baked in: ber-months seasonality, growth trend, weekly patterns).
Simulation — the prescriptive "what-if" layer for the decision-support side (e.g., "what happens to contacts if we raise spend 20%?"), which leans on the MLR coefficients.

Good question to nail down, because "simulation" is the vaguest of your four terms and a panelist may probe it. Strictly speaking, simulation isn't a single algorithm the way Holt-Winters is — it's a procedure that reuses your fitted models to answer hypothetical questions. In STRYX's case it works like this:
The core engine is your MLR chain. Once the regression is fitted on historical data, you have equations with concrete coefficients — conceptually: reach = β₀ + β₁·spend, contacts = α₀ + α₁·reach, purchases = γ₀ + γ₁·contacts. A "what-if" scenario is just pushing a hypothetical input through that chain: the user drags a slider to "spend = ₱80,000 in November," the system computes predicted reach, feeds that into the contacts equation, feeds that into purchases, and displays the projected funnel. That's called deterministic scenario analysis — same equations, hypothetical inputs. If that's all your simulation module does, the honest answer to "what algorithm does the simulation use?" is: "scenario propagation through the fitted multiple linear regression models."
The stronger version — and what I'd recommend you implement, because it's only ~20 lines of Python in your Flask service — is Monte Carlo simulation. The weakness of the deterministic version is that it outputs a single number ("₱80K gets you 5,412 contacts") with false precision. Monte Carlo fixes that: instead of running the chain once, you run it, say, 1,000 times, each time adding random noise drawn from your regression's residuals (the errors the model made on historical data). Each run gives a slightly different outcome; collect all 1,000 and you can report "₱80K projects to 4,800–6,100 contacts (90% interval), median 5,400." Now your DSS communicates uncertainty, which is what separates a decision-support system from a calculator — and it gives the Business Owner persona a risk picture, not just a point guess.
Two refinements that fit your architecture naturally: (1) layer the Holt-Winters seasonal factors into the scenario, so "₱80K in November" projects higher than "₱80K in February" — connecting your forecasting and simulation modules instead of leaving them siloed; (2) on the synthetic data, your residuals are well-behaved by construction, so the intervals will look clean — fine for the demo, and the same code works unchanged when real months accumulate.
For your documentation, the defensible phrasing is: "The simulation module performs Monte Carlo scenario analysis: user-specified marketing inputs are propagated through the fitted regression models with stochastic perturbation sampled from model residuals (n = 1,000 iterations), producing outcome distributions and confidence intervals rather than point estimates."
